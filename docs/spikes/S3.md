# Spike S3: preview frame inside the Tauri Workbench

> Status: **Complete on Windows (2026-10-20).** Both acceptance criteria are met in every Workbench origin tested. One assumption in ADR-0010 was wrong and is corrected: the preview iframe *does* get Tauri's IPC, and capability URL scoping is what refuses it. WebKitGTK (Linux) and WKWebView (macOS) runs are still open.

Machine: the developer's Windows 11 Pro PC. Tauri 2.12.4, WebView2 155, Node 26.12.0.

## Acceptance criteria (ROADMAP.md Phase 0)

| Criterion | Result |
|---|---|
| iframe loads and messages flow on Windows | **Met.** `bridge.hello` frame → Workbench and `inspect.set` Workbench → frame, with exact `targetOrigin` both ways |
| IPC call attempt from the frame is rejected | **Met.** Every command the frame tried was refused; a canary it tried to log never reached the Host |

## Method

`node scripts/spikes/s3-run.mjs` serves a deliberately hostile preview on `http://127.0.0.1:5899` and starts the Host with the Workbench's `PreviewFrameProbe` (shown only when `VITE_JESUTOBITS_PREVIEW_PROBE` is set). The probe frames the preview with ADR-0010's exact attributes:

```html
<iframe sandbox="allow-scripts allow-same-origin allow-forms allow-popups allow-modals allow-downloads"
        allow="" referrerpolicy="no-referrer" src="http://127.0.0.1:5899/?parent=…&nonce=…">
```

The preview knows the nonce, as a real preview would: the preview *is* the untrusted code, so the nonce only keeps out other origins. The page then:

1. sends a valid `bridge.hello`, one with a wrong nonce and one that fails the schema;
2. embeds forger frames from `http://127.0.0.1:5898` (other port) and `http://localhost:5899` (same port, other host name: the classic origin confusion), each posting a hello **with the correct nonce** straight to `window.top`;
3. tries every Tauri IPC route it can reach. Each attempt tries to write a canary string to the Host log through the `workbench_log` command, so a leak would be visible even if the call itself appeared to fail;
4. tries to read the Workbench DOM, then to navigate the Workbench away (`top.location`).

The harness passes only if one hello is accepted, every forgery is rejected, `inspect.set` reaches the frame from the exact Workbench origin, no canary appears in the Host log, and no DOM access or navigation succeeds in either direction.

|---|---|---|---|
| Dev | `http://127.0.0.1:1420` | `cargo build`; Vite started by the script (`--dev`) | 12/12 in 3 of 3 runs |

## Results

### Messaging (all modes)

Workbench summary, identical in all three modes apart from the origin:

```json
{"hellosAccepted":1,"rejected":{"source":2,"origin":0,"schema":1,"nonce":1},"frameDocumentReadable":false}
```

- The two forged hellos were rejected because they came from a window other than the preview iframe's `contentWindow` (`source`), before the origin check. The origin check (`127.0.0.1` vs `localhost`, other port, `https`) is covered by unit tests in `features/preview/frame-channel.test.ts`.
- The frame received `inspect.set` only from the exact Workbench origin, with the right nonce.

### IPC from the frame

| Attempt | Result (same in all modes) |
|---|---|
| `typeof window.__TAURI_INTERNALS__` in the frame | **`"object"`: Tauri injects its IPC into the iframe** |
| `__TAURI_INTERNALS__.invoke("workbench_log", …)` | Refused: `workbench_log not allowed on window "main", webview "main", URL: http://127.0.0.1:5899/ … allowed on: [windows: "main", URL: local]` |
| `invoke` of `rpc_call`, `runtime_subscribe`, `plugin:app\|version`, `plugin:event\|emit`, `plugin:webview\|webview_position`, `plugin:path\|resolve_directory` | Refused, same reason ("not allowed on … URL: http://127.0.0.1:5899/") |
| `invoke` of `plugin:window\|set_title`, `plugin:window\|minimize` | Refused (not granted at all) |
| `fetch("http://ipc.localhost/…")` with Tauri headers | `Failed to fetch` |
| `fetch(…, { mode: "no-cors" })` to `ipc.localhost` | Sent, no effect (no canary) |
| `window.chrome.webview.postMessage(…)` | **Present in the frame**; posted, no effect (no canary) |
| `window.parent.document`, `window.top.__TAURI_INTERNALS__` | Blocked: cross-origin frame |
| `top.location.href = …` | Blocked by the sandbox ("does not have permission to navigate the target frame") |
| Canary in the Host log | Never |

### What this changes

ADR-0010 assumed "Tauri's invoke key blocks IPC from sub-frames (RN-06)". That is not the mechanism. The frame has a working `invoke`; **the boundary is the capability's URL scope** (`URL: local`). Consequences:

- **No capability may ever grant a remote URL.** One `"remote": { "urls": ["http://127.0.0.1:*"] }` would hand the untrusted preview the Workbench's commands. `capabilities_never_grant_remote_urls` (Rust, every CI run) now fails if any capability file or inline capability does. It was checked by temporarily adding a remote grant to `capabilities/main.json`: the test failed as expected.
- Re-run `s3-run.mjs` on every Tauri upgrade. The URL scoping is Tauri's code, and a regression there would open the preview to IPC (RN-05 was such a bug).
- Commands the Workbench gets through `core:default` are equally reachable-but-refused, which supports trimming `core:default` (Phase 7).

### Mixed content

With `useHttpsScheme: true` the Workbench is `https://tauri.localhost`, and the `http://127.0.0.1` frame still loads and messages flow. WebView2 does not treat loopback as mixed content. The proxy-protocol fallback in ADR-0010 is not needed on Windows (RN-38).
