# Spike S1: Node sidecar lifecycle

> Status: **Complete on Windows (2026-10-20).** All four acceptance criteria are met, with one handshake outlier. Auto-restart with backoff carries into Phase 1, and one cold `pnpm dev` launch took 3.7 s to hand-shake (section 1), which Phase 1's startup work must explain.

Machine: the developer's Windows 11 Pro PC, not the NFR reference machine. Node 26.12.0, Rust 1.99.1, Tauri 2.12.4, WebView2 155.

## Acceptance criteria (ROADMAP.md Phase 0)

| Criterion | Target | Result |
|---|---|---|
| Handshake (spawn to `initialize` reply) | < 2 s | **Met in 7 of 8 launches:** 183–573 ms measured by the Host. One cold `pnpm dev` launch took 3.7 s (section 1) |
| Relay p95, 1 KB messages | < 5 ms | **Met.** The Host relay adds about 0.25 ms (p50) and 0.1–0.4 ms (p95) per round trip, so well under 1 ms per message |
| Orphans after 10 forced Host kills | 0 | **Met.** 0 of 10, with a runtime built to resist cleanup |
| 10k event inserts, `node:sqlite` WAL | < 2 s | **Met when batched.** 0.2–0.9 s in transactions; 2.1–2.5 s with one commit per row |

## 1. Handshake

Ten spawns straight from Node, `spawn()` to the `initialize` reply:

| Runtime artefact | Handshake (ms) | Bare `node -e 0` (ms) |
|---|---|---|
| Unbundled `tsc` output (`dist/main.js`, separate ESM modules incl. Zod) | 558–1193 | 216 |
| esbuild bundle (`dist/bundle/runtime.mjs`, 452 KB minified) | 178–312 | 107–141 |

Through the Host (`[host] runtime ready in … ms`, spawn to handshake): 183, 204, 305, 397, 514, 557, 573 ms across debug and release launches. The higher values were cold launches with the webview starting at the same time.

One launch through `pnpm dev`, straight after `cargo` had rebuilt the Host and while Vite was starting, took **3,707 ms**, over NFR-002's 2 s. The cause is not established. Candidates: CPU contention from the dev toolchain, and antivirus scanning the freshly copied 105 MB sidecar. NFR-002 applies to the reference machine and an installed build, but Phase 1's startup work (NFR-001) should time each stage (spawn, first stdout byte, reply) to find out.

Module loading dominates on Windows (many small files, each scanned by antivirus). Under a parallel Vitest run the unbundled runtime took 2.2 s, over NFR-002. So the sidecar always runs the bundle (ADR-0013 note), and `RuntimeHarness` spawns the bundle so tests measure what ships. Node's module compile cache (`module.enableCompileCache()`) has not been tried yet.

## 2. Relay latency (NFR-006)

`runtime.ping` echoes its payload, so each round trip carries the payload both ways. 1,000 sequential calls after 50 warm-up calls, on an idle machine.

| Path, 1 KB payload | p50 (ms) | p95 (ms) | How |
|---|---|---|---|
| Node → runtime over stdio (no Host) | 0.31 | 0.55–0.67 | `node scripts/spikes/s1-stdio-latency.mjs` |
| Host `Connection` → runtime (no webview), debug build | 0.53–0.61 | 0.69–1.10 | `cargo test relay_latency -- --ignored --nocapture` |
| Webview IPC alone (`plugin:app\|version`, never reaches the runtime), release | 3.0–3.7 | 3.8–5.5 | Stand-in page, see below |
| Full path: Workbench → Host → runtime → back, release | 4.2–4.3 | 5.1–9.4 | Stand-in page, see below |

The relay's own cost is the difference between the first two rows: about 0.25 ms per round trip (two messages) at p50, even unoptimised. **NFR-006 ("Host relay adds under 5 ms p95 per runtime message") is met by a wide margin.**

The end-to-end Workbench call is dominated by Tauri's webview IPC on WebView2, about 3 to 4 ms per `invoke` round trip, before any of our code runs. Consequences:

- UI code must not make chatty `rpc` calls in loops (for example per row or per keystroke). Batch, or stream through events.
- Runtime → Workbench streams already use a Tauri `Channel`, not `invoke`. The event path's latency and throughput were **not** measured here, because no runtime events exist yet. Measure it in Phase 2 with `model.text_delta` (ADR-0003's revisit trigger concerns token streaming).

64 KB payloads: 1.3–1.5 ms over direct stdio, 8–14 ms through the debug-build relay (unoptimised `serde_json`), and 9.5–10.4 ms p50 end to end in release. Large payloads should stay rare; methods page big data anyway (ADR-0003, decision 7).

The stand-in page: while the npm registry was unreachable, a page served on the dev port called `window.__TAURI_INTERNALS__.invoke`, the function `@tauri-apps/api`'s `invoke` wraps, with the same `rpc_call` command. Once the packages installed, the real Workbench benchmark (`features/diagnostics/relay-benchmark.ts`, run with `VITE_JESUTOBITS_BENCH=relay pnpm dev`, debug Host) gave 1 KB **p50 5.1 ms, p95 6.7 ms, p99 8.8 ms**. That matches the stand-in page's debug-build numbers (p50 4.6–4.9, p95 5.6–7.2), so the stand-in measured the same path.

The same page confirmed the allowlist end to end: `rpc_call("runtime.shutdown")` from the Workbench was refused with `rpc.method_not_allowed`.

## 3. Orphan processes (NFR-010, ADR-0011)

`node scripts/spikes/s1-orphans.mjs` starts the debug Host with `fixtures/bin/fake-runtime.mjs` (debug-only `JESUTOBITS_RUNTIME_ENTRY` override). That runtime starts a grandchild and **ignores stdin EOF**, so the job object is the only thing that can clean up. The script then kills the Host with `taskkill /F` (`TerminateProcess`, what Task Manager's End task does).

| Mode | Trials | Orphaned | Tree gone after kill |
|---|---|---|---|
| Job object (normal) | 10 | **0** | 314–919 ms, including the time to start `taskkill.exe` itself |
| Control: job object disabled (`--control`, debug only) | 3 | 3 (runtime and grandchild every time) | n/a |

The control shows the test can see an orphan at all, and confirms RN-03 for our setup: nothing but the job object cleans up after a killed Host. `cargo test` also checks on every Windows CI run that closing the job kills an assigned process and its grandchild (`job_object_windows::tests`).

Earlier, during manual checks, one Host launched from Git Bash left the real runtime running for at least 2 s after `taskkill /F`, with an empty Host log. It did not reproduce in two further manual trials or in the 10 scripted trials, and the real runtime also exits on stdin EOF. The cause is unknown; if it recurs in the nightly desktop test, capture the Host log and job membership (`IsProcessInJob`) when it happens.

## 4. `node:sqlite` with WAL

`node scripts/spikes/s1-sqlite-bench.mjs`: 10,000 runtime-event-shaped rows (about 400 bytes of JSON each), `journal_mode=WAL`, `synchronous=NORMAL`, three runs each.

| Write pattern | Best (ms) | Worst (ms) | Within 2 s |
|---|---|---|---|
| One transaction | 202 | 942 | Yes |
| A transaction per 100 rows | 235 | 418 | Yes |
| Autocommit (one commit per row) | 2130 | 2530 | No |

A single-row commit costs about 0.2 ms. That is fine at agent pace (a few events per second), but bursts such as tool output must be grouped into one transaction per flush. Recorded in DATA_AND_PERSISTENCE.md.

## 5. What the Host now does

- Spawns the Node sidecar with the ADR-0011 environment allowlist (`NODE_OPTIONS` and everything else dropped), `CREATE_NO_WINDOW` and `--stdio --data-dir <dir>` (ADR-0002).
- Assigns it to a kill-on-close job object **before** `runtime.initialize`, with a non-inheritable job handle.
- Handshake with a 10 s timeout and a protocol major-version check; status `starting` → `ready`, or `failed` with a reason.
- Health pings every 5 s (2 s timeout); two misses → `degraded`, an answer → `ready`.
- Graceful shutdown on app exit: `runtime.shutdown`, wait up to 5 s, then kill. Checked by closing the `pnpm dev` window (WM_CLOSE): the runtime exited with code 0 and no Jesutobits or Vite process remained.
- Relays Workbench calls only for methods in the generated allowlist; refuses reverse `host.*` calls until they are implemented; streams events and status over Channels; caps messages at 4 MiB in both directions.
- Capabilities: the main window can call only `rpc_call`, `runtime_subscribe` and `workbench_log` beyond `core:default` (trimmed in Phase 7). No shell, fs or http plugins.
