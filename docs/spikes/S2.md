## Method

`node scripts/spikes/s2-run.mjs`:

1. Starts `fixtures/projects/vite-react-tailwind` through `packages/preview-launcher` with the user's Node. The launcher resolves Vite **from the project** and calls `createServer({ root, server: { host: "127.0.0.1", port, strictPort: true }, plugins: [jesutobitsVisualEdit({ root })] })` without `configFile`, so the project's own `vite.config.ts` is loaded and our plugin is added inline (RN-23).
2. Opens the page in headless Edge (the browser ADR-0010 uses for agent checks).
3. Samples 20 instrumented elements evenly. Covered on purpose: multi-line opening tags, self-closing `<img />`, a `map()` list (one location, three DOM nodes), a custom element (`<status-badge>`), a fragment-rooted arrow component, a `cn()` computed `className`, and **a file with CRLF line endings** (`Counter.tsx`).
4. Applies one Tailwind class change (`text-4xl` → `text-6xl` on the hero `<h1>`) with `applyClassEdit` from `packages/services/src/visual/source-transformer.ts`, writes the file and times the update. Before the edit it clicks a counter twice and sets a marker on `window`, so a full reload would be detected.
5. Restores the file.

## Findings

### RN-24: inline plugins are appended after the config file's plugins

Verified. Inline `plugins` are merged with the project's, but they come **after** them, even among plugins with the same `enforce: "pre"`. Resolved order in the fixture:

```
4  vite:react-babel          (pre)
5  vite:react-refresh-fbm    (pre)
6  vite:react-refresh        (pre)
7  @tailwindcss/vite:scan
8  @tailwindcss/vite:generate:serve
9  jesutobits:visual-edit    (pre, inline)
```

This did not matter here: in `@vitejs/plugin-react` 6.1.2, `vite:react-babel` has **no `transform` hook**. It only configures Vite core's Oxc JSX transform, which runs after every `pre` plugin (RN-39). But a project with another early plugin that compiles JSX (for example Babel with the React Compiler) could compile it before we see it. So the plugin's transform now uses hook-level `order: "pre"`, which runs before every default-order `transform` hook regardless of array position. A plugin that also uses `order: "pre"` and compiles JSX would still run first; such projects fall back to "Inspect-only" in Phase 5 (detect: zero instrumented elements on a page with JSX).

The wrapper-config fallback in ADR-0009 is **not needed**.

### Parser: Babel, not Oxc

ADR-0009 allowed "an Oxc or Babel parser". The plugin runs in the user's toolchain and must be a self-contained JS bundle (VISUAL_EDITING.md section 4.8). `oxc-parser` is a native addon that cannot be inlined into plain JavaScript, so the plugin bundles `@babel/parser` and `magic-string` (336 KB minified, `scripts/build-guest.mjs`, target Node 20.19). Instrumentation at under 1 ms per file leaves the 5 ms budget plenty of room.

### Smaller findings

- `@vitejs/plugin-react` does not export `./package.json`; Vite does. The launcher's `require.resolve("vite/package.json")` works, but resolving other packages that way will not. Phase 4 should fall back to walking up from the resolved entry.
- One JSX location renders many DOM nodes (`article` in the list: three nodes, one `loc`), as designed. Instance counts come in Phase 5.
